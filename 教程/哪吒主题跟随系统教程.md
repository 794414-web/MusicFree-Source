# 哪吒主题跟随系统教程

本文说明 Android 应用如何跟随哪吒车机的日间/夜间主题。核心原则是：主题变化广播只表示“发生了变化”，不能当作最终主题值；应用必须在启动时和收到变化通知后主动读取一次当前状态。

## 一、工作原理

哪吒系统常用以下状态来源：

- `persist.sys.theme_night_mode=night_mode_on`：强制夜间模式
- `persist.sys.theme_night_mode=night_mode_off`：强制日间模式
- `persist.sys.theme_night_mode=night_mode_auto`：自动模式
- 自动模式下，可结合 `persist.sys.theme.from.map` 判断当前实际结果：`night_mode` 表示夜间，`day_mode` 表示日间

系统主题变化时，可监听：

```text
com.hozonauto.thememanager.ACTION_HOZON_THEME_CHANGED
```

部分系统设置流程还可能使用带有 `FOR_SETTING` 后缀的通知。不要依赖广播 extra 直接决定界面主题；无论收到哪一种通知，都重新读取状态。

> `android.content.res.Configuration.uiMode` 是通用 Android 主题信息来源，也应作为兼容回退。但在哪吒车机上，系统主题管理器的持久化属性是更直接的状态来源。读取隐藏的 `SystemProperties` 需要系统权限或系统侧放行；普通应用应改用车机提供的公开接口，不能假设反射一定可用。

## 二、封装主题状态读取

下面的 Kotlin 示例通过反射读取系统属性，避免在普通 SDK 编译时直接依赖隐藏 API。读取失败时回退到 `Configuration.uiMode`：

```kotlin
import android.content.Context
import android.content.res.Configuration

object NezhaThemeState {
    private const val NIGHT_MODE_PROPERTY = "persist.sys.theme_night_mode"
    private const val MAP_THEME_PROPERTY = "persist.sys.theme.from.map"

    private const val NIGHT_ON = "night_mode_on"
    private const val NIGHT_OFF = "night_mode_off"
    private const val NIGHT_AUTO = "night_mode_auto"

    fun isNight(context: Context): Boolean {
        val configured = readProperty(NIGHT_MODE_PROPERTY, NIGHT_AUTO)
        return when (configured) {
            NIGHT_ON -> true
            NIGHT_OFF -> false
            NIGHT_AUTO -> readProperty(MAP_THEME_PROPERTY, "day_mode") == "night_mode"
            else -> isAndroidNight(context)
        }
    }

    private fun isAndroidNight(context: Context): Boolean {
        val mask = context.resources.configuration.uiMode and
            Configuration.UI_MODE_NIGHT_MASK
        return mask == Configuration.UI_MODE_NIGHT_YES
    }

    private fun readProperty(key: String, defaultValue: String): String {
        return runCatching {
            val clazz = Class.forName("android.os.SystemProperties")
            val method = clazz.getMethod("get", String::class.java, String::class.java)
            method.invoke(null, key, defaultValue) as? String ?: defaultValue
        }.getOrDefault(defaultValue)
    }
}
```

如果应用明确是系统应用，并且构建环境提供了对应 API，可以直接调用 `SystemProperties.get`；仍然应保留默认值和异常回退。

## 三、启动时和系统变化时主动同步

使用一个动态接收器，并将“读取状态”和“应用主题”放在同一个方法中：

```kotlin
class ThemeFollowController(
    context: Context,
    private val applyTheme: (night: Boolean) -> Unit
) {
    private val appContext = context.applicationContext
    private var registered = false

    private val receiver = object : BroadcastReceiver() {
        override fun onReceive(context: Context, intent: Intent) {
            if (intent.action == ACTION_THEME_CHANGED) {
                syncFromSystem()
            }
        }
    }

    fun start() {
        if (registered) return
        syncFromSystem() // 启动时主动读取，不能等待广播

        val filter = IntentFilter(ACTION_THEME_CHANGED)
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU) {
            appContext.registerReceiver(receiver, filter, Context.RECEIVER_EXPORTED)
        } else {
            @Suppress("DEPRECATION")
            appContext.registerReceiver(receiver, filter)
        }
        registered = true
    }

    fun stop() {
        if (!registered) return
        appContext.unregisterReceiver(receiver)
        registered = false
    }

    private fun syncFromSystem() {
        applyTheme(NezhaThemeState.isNight(appContext))
    }

    private companion object {
        const val ACTION_THEME_CHANGED =
            "com.hozonauto.thememanager.ACTION_HOZON_THEME_CHANGED"
    }
}
```

Activity、Service 或自定义 View 宿主都可以持有这个控制器。界面宿主通常在 `onStart` 中启动、在 `onStop` 中停止；长期存在的播放器或悬浮窗服务则可以跟随服务生命周期注册。

## 四、应用主题而不是只刷新颜色

`applyTheme` 应完成应用自身的主题切换。例如 Compose 应用可以更新一个 `StateFlow<Boolean>`，由顶层主题根据该值选择 `lightColorScheme` 或 `darkColorScheme`；传统 View 应用可以更新主题资源并重新创建需要重新加载资源的 Activity。

不要只调用一次 `recreate()` 就认为完成了同步。应先读取到新状态，再更新状态容器，最后决定哪些界面需要重建。这样可以避免广播到达顺序变化时短暂使用错误主题。

## 五、最佳实践

1. 启动时先读一次，注册广播后再次读一次也可以，用于覆盖注册窗口内发生的变化。
2. 广播回调只作为触发器，不读取广播 extra 作为主题真值。
3. 明确处理 `on`、`off`、`auto` 和未知值；未知或读取失败时使用 `uiMode` 或产品定义的安全默认值。
4. 动态注册与反注册成对出现，避免 Activity 销毁后仍持有 Context。
5. 不要频繁写系统主题属性。跟随系统的应用只读状态，不应在收到变化广播后再次写回系统。
6. 主题读取和 UI 更新应在主线程协调；读取系统属性若在目标设备上可能阻塞，可先在后台读取，再把最终状态投递到主线程。
7. 生产包中验证系统权限、属性访问限制和不同系统版本；普通三方应用无法读取属性时，应向车机平台索取公开主题接口。

## 六、排查清单

- 冷启动时没有广播，界面是否仍能正确显示当前主题。
- 收到广播后是否重新读取了属性或 `uiMode`。
- 自动模式下是否读取了实际映射状态，而不是把 `auto` 误当成日间。
- Activity 重建或 Compose 状态更新后，窗口、弹窗和多屏界面是否也同步。
- 多次启动/停止后是否发生重复回调或反注册异常。
