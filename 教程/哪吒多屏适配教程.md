# 哪吒多屏适配教程

本文说明 Android 应用如何适配哪吒车机的主屏、副驾屏和 HUD。重点是先判断目标屏是否存在，再根据实际 `Display` 创建对应上下文；不能把某个 display ID 永久当作某一种屏幕。

## 一、工作原理

Android 通过 `DisplayManager` 提供当前系统可见的屏幕列表。每个 `Display` 有一个运行时 `displayId`，应用应完成以下流程：

1. 获取 `DisplayManager`。
2. 枚举当前可用的 `Display`。
3. 按产品需要识别主屏、普通副屏和 HUD。
4. 取到目标 `Display` 后调用 `Context.createDisplayContext(display)`。
5. 用新上下文获取资源、密度、`WindowManager` 和创建窗口。

主屏通常是 `Display.DEFAULT_DISPLAY`，即 ID `0`。副屏和 HUD 的 ID 可能因车型配置、系统版本或是否存在其它屏幕而变化。尤其是只有 HUD 的设备，HUD 可能成为第一块次屏，不能无条件写死为 `2`。

## 二、通过 properties 判断屏幕能力

哪吒系统提供只读 system property 表示车辆配置的屏幕能力：

| Property | 值为 `1` 时 | 其它值 |
| --- | --- | --- |
| `ro.hozon.car.psd` | 配置了副驾屏能力 | 没有副驾屏能力 |
| `ro.hozon.car.arhud` | 配置了 HUD 能力 | 没有 HUD 能力 |

这里判断的是“系统配置了什么能力”，不是“目标 `Display` 当前一定存在”。完整判断必须同时满足：

1. property 表示该角色已配置。
2. `DisplayManager` 能找到对应的实际 `Display`。

Property 是只读配置，应用只读取，不要尝试写回。普通应用如果无法访问 `SystemProperties`，应使用车机平台提供的公开能力接口；下面的反射读取仅用于避免对隐藏 API 产生编译期依赖。

```java
import java.lang.reflect.Method;

private static final String PROP_VICE_DISPLAY = "ro.hozon.car.psd";
private static final String PROP_HUD_DISPLAY = "ro.hozon.car.arhud";

public static boolean hasViceDisplay() {
    return getSystemPropertyInt(PROP_VICE_DISPLAY, 0) == 1;
}

public static boolean hasHudDisplay() {
    return "1".equals(getSystemProperty(PROP_HUD_DISPLAY, "0"));
}

private static String getSystemProperty(String key, String defaultValue) {
    try {
        Class<?> clazz = Class.forName("android.os.SystemProperties");
        Method method = clazz.getMethod("get", String.class, String.class);
        Object result = method.invoke(null, key, defaultValue);
        return result instanceof String ? (String) result : defaultValue;
    } catch (Throwable ignored) {
        return defaultValue;
    }
}

private static int getSystemPropertyInt(String key, int defaultValue) {
    try {
        return Integer.parseInt(getSystemProperty(key, String.valueOf(defaultValue)));
    } catch (RuntimeException ignored) {
        return defaultValue;
    }
}
```

## 三、判断和查找屏幕

下面的 Java 示例只使用公开 Android API，并提供“指定角色”和“任意次屏”两种策略。实际产品如果有可靠的屏幕角色标识，应优先使用角色标识；没有时，至少检查 `Display` 是否真实存在。

```java
import android.content.Context;
import android.hardware.display.DisplayManager;
import android.view.Display;

public final class MultiDisplaySupport {
    private MultiDisplaySupport() {}

    public static Display[] getDisplays(Context context) {
        DisplayManager manager =
                (DisplayManager) context.getSystemService(Context.DISPLAY_SERVICE);
        return manager == null ? new Display[0] : manager.getDisplays();
    }

    public static Display findSecondaryDisplay(Context context) {
        for (Display display : getDisplays(context)) {
            if (display != null && display.getDisplayId() != Display.DEFAULT_DISPLAY) {
                return display;
            }
        }
        return null;
    }

    public static Display findDisplay(Context context, int displayId) {
        DisplayManager manager =
                (DisplayManager) context.getSystemService(Context.DISPLAY_SERVICE);
        return manager == null ? null : manager.getDisplay(displayId);
    }
}
```

这里的 `findSecondaryDisplay` 只表示“第一块可用次屏”，不表示它一定是副驾屏或 HUD。正确的使用方式是先调用 `hasViceDisplay()` 或 `hasHudDisplay()` 判断能力，再查找并确认实际 `Display`。若业务必须区分两者，应使用平台提供的角色信息、屏幕特征或经过验证的车型适配表，并在找不到或角色不明确时回退主屏。

不要把 property 和 display ID 直接绑定成固定规则。例如，只有 HUD 的设备上，HUD 可能使用 ID `1`；副驾屏和 HUD 同时存在时，HUD 也可能使用 ID `2`。应按当前 `DisplayManager.getDisplays()` 的结果解析实际 ID：

```java
public static Display findHudDisplay(Context context) {
    if (!hasHudDisplay()) {
        return null;
    }
    return findSecondaryDisplay(context);
}

public static Display findViceDisplay(Context context) {
    if (!hasViceDisplay()) {
        return null;
    }
    return findSecondaryDisplay(context);
}
```

上面的两个函数只适合“目标设备只有一种次屏角色”这一简单情况。若副驾屏和 HUD 同时存在，必须在 `findSecondaryDisplay` 基础上加入角色排除和识别逻辑：先解析 HUD，再从剩余次屏中解析副驾屏，不能让两个角色拿到同一个 `Display`。

## 三、创建目标屏上下文

拿到目标 `Display` 后，应使用该屏上下文获取屏幕相关资源和系统服务：

```kotlin
fun createContextForDisplay(base: Context, display: Display?): Context {
    return if (display == null ||
        display.displayId == Display.DEFAULT_DISPLAY
    ) {
        base
    } else {
        base.createDisplayContext(display)
    }
}

fun getWindowManagerForDisplay(base: Context, display: Display): WindowManager {
    val displayContext = base.createDisplayContext(display)
    return displayContext.getSystemService(WindowManager::class.java)
        ?: error("WindowManager unavailable for display ${display.displayId}")
}
```

如果目标屏不可用，返回原始 Context 是合理的降级方式，但调用方必须知道自己已经回退主屏，不能继续把它当作目标屏使用。

创建多屏悬浮视图时，典型流程如下：

```kotlin
fun showOnDisplay(base: Context, display: Display, view: View) {
    val displayContext = base.createDisplayContext(display)
    val windowManager = displayContext.getSystemService(WindowManager::class.java)
        ?: return

    val params = WindowManager.LayoutParams(
        240,
        120,
        WindowManager.LayoutParams.TYPE_APPLICATION_OVERLAY,
        WindowManager.LayoutParams.FLAG_NOT_FOCUSABLE,
        PixelFormat.TRANSLUCENT
    )
    windowManager.addView(view, params)
}
```

创建、移除窗口必须使用同一个目标屏的 `WindowManager`。销毁时保存每个 `displayId` 对应的窗口和管理器，不能拿主屏的管理器去移除副屏窗口。

## 四、监听屏幕变化

副驾屏或 HUD 可能在应用启动后才出现，也可能暂时断开。用 `DisplayManager.DisplayListener` 监听变化，并重新枚举屏幕：

```kotlin
class DisplayChangeController(
    context: Context,
    private val refresh: () -> Unit
) {
    private val manager =
        context.getSystemService(DisplayManager::class.java)
            ?: error("DisplayManager unavailable")

    private val listener = object : DisplayManager.DisplayListener {
        override fun onDisplayAdded(displayId: Int) = refresh()
        override fun onDisplayRemoved(displayId: Int) = refresh()
        override fun onDisplayChanged(displayId: Int) = refresh()
    }

    fun start() = manager.registerDisplayListener(listener, null)
    fun stop() = manager.unregisterDisplayListener(listener)
}
```

`refresh` 中应先移除已经失效的窗口，再重新读取可用屏幕并创建窗口。刷新操作应在主线程串行执行，避免屏幕增删同时发生时重复添加 View。

## 五、HUD 适配注意事项

HUD 是一个可用的 `Display`，但它不一定适合承载普通应用页面。通常只在 HUD 上创建尺寸固定、内容简单的专用窗口，并避免把主屏的布局尺寸、字体密度和触摸交互直接复制过去。

如果产品只需要“任意可用次屏”，可以按优先级选择 HUD、再选择副驾屏；如果产品必须显示在副驾屏，则必须排除 HUD。两种需求不要共用一个没有角色语义的“第一个次屏”函数。

## 六、最佳实践

1. 每次使用前确认 `Display` 非空且仍然有效；屏幕列表是动态的。
2. 不要只通过 `displayId == 1` 或 `displayId == 2` 判断角色，除非该映射已在目标系统上验证并且有明确回退。
3. 资源、密度、`WindowManager` 和窗口创建都从目标 `displayContext` 获取。
4. 以 `displayId` 为键保存窗口实例，屏幕移除时立即释放对应窗口和引用。
5. 屏幕切换、插拔和重建操作应幂等：重复刷新不能添加重复 View。
6. 对 HUD 和副驾屏分别定义能力、角色和布局策略；“屏幕存在”不等于“业务适合显示”。
7. 目标屏不可用时回退主屏，并在业务状态中明确标记回退结果，避免用户以为内容已经显示在目标屏。
8. 涉及悬浮窗时确认悬浮窗权限、窗口类型、透明格式和目标屏的窗口令牌要求；权限不足时应停止创建并给出可执行提示。

## 七、排查清单

- 启动时打印当前所有 `displayId` 和 `Display` 状态。
- 屏幕出现、消失和状态变化时是否触发重新枚举。
- 目标屏上的 `resources.displayMetrics` 是否来自目标上下文。
- 窗口移除时是否使用创建它的同一个 `WindowManager`。
- 只有 HUD、只有副驾屏、两者同时存在、没有次屏四种情况是否都能正确降级。
